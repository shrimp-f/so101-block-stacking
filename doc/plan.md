# SO-101 積み木スタッキング シミュレータ環境 構築計画

## 1. 目的

LeRobot の SO-101 アームを用いて「積み木ブロックをできるだけ高く積み上げる」タスクのシミュレータ環境を構築する。
環境はすべて Docker コンテナ内で再現可能にし、以下の流れを一貫して回せることをゴールとする。

1. シミュレーション上で SO-101 + ブロックのシーンを動かす
2. スクリプト（IK ベースの熟練者ポリシー）でデモデータを自動生成し、LeRobot Dataset 形式で保存する
3. LeRobot の模倣学習ポリシー（ACT / Diffusion Policy）を学習・評価する
4. 積み上げ段数を指標として性能を測る

## 2. 前提となるホスト環境（調査結果）

| 項目 | 値 | 影響 |
|---|---|---|
| OS | Windows 10 Home 22H2 (19045) | Docker Desktop + WSL2 バックエンドが必要 |
| GPU | GeForce GTX 1070 (8GB), Driver 560.94 | CUDA 利用可。RTX 必須の Isaac Sim は不可 → **MuJoCo を採用** |
| RAM | 16GB | 学習時のバッチサイズに注意。WSL2 のメモリ上限を設定する |
| CPU | Core i7-7700 | 物理シミュレーションは十分 |
| Docker | **未インストール** | Docker Desktop を導入する |
| WSL | Ubuntu-18.04 (WSL1) のみ | WSL2 への更新が必要（Docker Desktop が自動で使う） |

> Windows 10 では WSLg（Linux GUI 表示）が使えないため、コンテナ内の画面表示は
> **オフスクリーン描画（EGL）＋ 動画保存** と **ブラウザ経由の可視化（noVNC）** で行う。

## 3. 技術選定

| 要素 | 採用 | 理由 |
|---|---|---|
| 物理エンジン | MuJoCo 3.x | 軽量・GTX 1070 で動作・LeRobot のシミュ環境と相性が良い |
| ロボットモデル | SO-101 の MJCF（TheRobotStudio/SO-ARM100 リポジトリの `Simulation/SO101`） | 公式モデル。実機キャリブレーションと関節範囲が一致 |
| 環境 API | Gymnasium | LeRobot の `gym_*` 環境と同じインターフェイス |
| データ形式 | LeRobotDataset (v3) | LeRobot の学習スクリプトがそのまま使える |
| 学習 | LeRobot（ACT → Diffusion Policy） | ACT は 8GB VRAM で学習可能 |
| 可視化 | 動画出力（mp4）＋ Rerun / noVNC | Windows 10 でも表示可能 |
| コンテナ | `nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04` ベース, Python 3.10 | LeRobot の推奨 Python バージョン |

## 5. Docker 環境設計

### 5.1 ホスト側の準備（手動作業）
1. Windows Update で最新化
2. `wsl --update` / `wsl --set-default-version 2` で WSL2 を有効化
3. Docker Desktop for Windows をインストール（WSL2 バックエンド）
4. `%UserProfile%\.wslconfig` で WSL2 のメモリを 10〜12GB に設定
5. 動作確認: `docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi`

### 5.2 イメージ構成
- ベース: `nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04`
- システムパッケージ: `python3.10`, `ffmpeg`, `libegl1`, `libgl1`, `libosmesa6`, `git`
- 可視化用（任意）: `xvfb`, `x11vnc`, `novnc` を入れ、`localhost:6080` でブラウザから MuJoCo viewer を操作
- Python: `torch`（CUDA 12.x 版）, `lerobot`, `mujoco`, `gymnasium`, `rerun-sdk`
- 環境変数: `MUJOCO_GL=egl`（GPU オフスクリーン描画。失敗時は `osmesa` にフォールバック）

### 5.3 docker-compose
- `deploy.resources.reservations.devices` で GPU を割り当て
- `./` を `/workspace` にマウント（ソースはホストで編集、コンテナで実行）
- `data/`, `outputs/`, HuggingFace キャッシュを永続化
- ポート: `6080`（noVNC）, `9876`（Rerun web viewer）
- `shm_size: 8gb`（DataLoader 用）

## 6. タスク定義

### 6.1 シーン
- テーブル上に SO-101 を固定
- ジェンガのサイズのブロック（7.5 × 2.5 × 1.5cm）を N 個（初期 3 個 → 最大 9〜10 個）、平らに寝かせてランダム位置・向きで配置
- 積み上げ目標位置（ベース）は固定 or ランダム
- カメラ: 俯瞰の固定カメラ（front）＋ リストカメラ（wrist）。実機の LeRobot 構成に合わせる

### 6.2 観測・行動空間（LeRobot 形式に合わせる）
- `observation.state`: 6 関節角（5 軸 + グリッパ）
- `observation.images.front`, `observation.images.wrist`: 例 480×640 RGB（学習時は縮小）
- `action`: 6 関節の目標角（実機 SO-101 と同じ絶対位置指令）
- 制御周期: 30Hz（実機の記録周期と合わせる）

### 6.3 報酬・成功判定
- 段数 = 最下段から連続して積まれ、静止しているブロックの数
- 成功: 目標段数に到達し、数秒間崩れずに静止
- 疎な報酬（段数増加時 +1）を基本とし、強化学習を行う場合は把持・持ち上げの密な報酬を追加

### 6.4 カリキュラム
| レベル | 内容 |
|---|---|
| L1 | 1 個のブロックを掴んで持ち上げる |
| L2 | 2 段積み（1 個を別の 1 個の上に置く） |
| L3 | 3 段積み |
| L4 | 5 段以上（ジェンガのブロックで最大 9〜10 段の見込み。SO-101 の届く高さが上限） |

- **完了条件**: コンテナ内で MuJoCo の EGL 描画画像が保存でき、torch が GPU を認識する

### Phase 1: SO-101 単体シミュレーション
- [x] SO-101 MJCF を取得し `assets/so101/` に配置（`scripts/fetch_so101.sh`、SO-ARM100 commit a758567）
- [x] 関節を動かす動画を出力し、可動範囲・グリッパ動作を確認（`scripts/view_scene.py` → `outputs/phase1/joint_sweep.mp4`）
- [x] アクチュエータゲイン・関節範囲を確認（kp=998, 最大トルク ±3.35Nm。STS3215 の定格 約 2.9Nm と同程度）
- **完了条件**: 関節指令どおりに動く mp4 が出力できる → 達成

結果メモ:
- 静止時の追従誤差はどの関節も 0.03° 以下。shoulder_lift と elbow_flex を上限まで動かすとグリッパが床に当たって止まる（40〜60° の誤差）。これは物理的に正しい挙動
- 元のメッシュは約 32 万ポリゴンあり、CPU 描画で 4 fps しか出ない。描画用メッシュだけを間引き（約 9.4 万ポリゴン、`scripts/make_lowpoly.py`）、
  影マップを 2048 に、アンチエイリアスをなしにして **640x480 で約 15〜18 fps**。影を切ると約 50 fps
- WSL の d3d12 ドライバによる GPU 描画は、コンテナ内でドライバの読み込みに失敗したため見送り
- 関節の単位はラジアン、ゼロ点は可動範囲の中央。実機の LeRobot は度数（グリッパは 0〜100）なので、Phase 2 の環境で変換する

Phase 2 への申し送り:
- 衝突判定はメッシュの凸包になる。グリッパの固定ジョー・可動ジョーの凸包がブロックの把持に向かない可能性が高いので、
  指先にボックス形状の衝突 geom を追加して把持を安定させる

### Phase 2: 積み木シーンと Gymnasium 環境
- [x] テーブル・ブロック・カメラを含むシーン（XML ではなく MjSpec で組み立てる: `so101_stack/envs/scene.py`）
- [x] `stack_env.py`（reset でランダム配置、step、観測、段数判定）。Gym ID `so101_stack/StackBlocks-v0`
- [x] 接触パラメータ調整（摩擦・`solref`/`solimp`・タイムステップ）で把持時のすべり／貫通を抑える
- [x] 逆運動学（`so101_stack/controllers/ik.py`、減衰最小二乗法）を Phase 3 から前倒しで作成
- **完了条件**: ランダム行動で 1000 ステップ回してもシミュレーションが破綻しない → 達成（`scripts/test_env.py`）

実装メモ:
- 観測・行動は LeRobot の SO-101 実機と同じ単位（腕は度数、グリッパは 0=閉〜100=開）。
  観測は `agent_pos` + `pixels/{front,wrist}`（または `environment_state` = ブロックの位置姿勢）
- 物理: timestep 1/600 s（30Hz 制御で 20 サブステップ）、implicitfast、楕円摩擦錐、impratio 10
- ブロック: **ジェンガのサイズ（長さ 7.5cm × 幅 2.5cm × 厚さ 1.5cm、15g、木目調）**。平らに寝かせて同じ向きで 1 列に積み、
  幅の方向を挟んで掴む。高い段は傾けた姿勢で置くためジョーの閉じる方向が固定され、段ごとに 90° 交差させる積み方はしない。
  摩擦は木どうし 0.5、木とテーブル 0.6。リセット時に x 0.12〜0.28m, y ±0.16m にランダム配置（向きもランダム）
  - 最初は 3cm の立方体で作り、2026-11-02 にジェンガのサイズへ変更した
- 指先パッド: 固定ジョー・可動ジョーの内面に厚さ 3mm・長さ 3.2cm の箱形の当たり判定（摩擦 1.5）。
  ジョーのメッシュ（凸包）はブロックと接触しないように衝突フィルタで除外
- 接触の硬さ: 既定のままだとグリッパを押し付けたときに 24mm めり込んだため、テーブル・ブロック・パッドの
  solref を 0.004 に（ランダム行動での最大めり込み 6mm。残りは腕のメッシュとの接触）
- カメラ: front（右前方の斜め上から作業領域を見下ろす）と wrist（公式モデルのリストカメラと同じ位置）
- 成功判定: 目標段数に達し、グリッパのパッドが触れておらず、ブロックが 0.5 秒静止

把持テスト（`scripts/test_grasp.py`、逆運動学 + 直線軌道で 2 段積み）:
- ジェンガのブロックで 10 seed 中、掴んで持ち上げるのは 10/10 成功（持ち上げ時のすべり 1.5mm 以下）。2 段積みの成功は 9/10
  （3cm の立方体のときは 7/10、すべり 約 4mm）
- 失敗 1 件は、置く位置（ベースから 31cm）が真下向きの姿勢では届かないことによる逆運動学の失敗
- 掴むときは把持点をジョーが開く方向に 8mm ずらして下ろす必要がある（ずらさないと固定ジョーがブロックに乗り上げる）
- 厚さ 1.5cm のブロックを掴むとき、把持点（指先パッドの中央）はブロック中心の 1.35cm 上。指先はテーブルの約 2mm 上になる

届く範囲（`scripts/reach_map.py`）:
- 真下向きの姿勢で把持点が届くのは高さ約 10cm まで（ベースから 18〜24cm）。遠いほど低くなる
- ジョーの閉じる方向を水平に保ったまま指を 20〜40° 傾けると、高さ約 16cm（ベースから 26〜32cm）まで届く
- ジェンガのブロック（厚さ 1.5cm）では、k 段目を置くときの把持点の高さは 0.021 + 0.015 × (k − 1) m。
  真下向きで 6 段目（約 9.6cm）まで、傾ければ 9〜10 段目（約 14〜16cm）まで届く見込み

Phase 3 への申し送り:
- 積み上げ位置を固定する（ベースから 22〜26cm 付近）。低い段は真下向き、高い段は傾けた姿勢で置く
- 傾けた姿勢ではジョーの閉じる方向がタワーの位置での接線方向に固定されるので、
  1 段目を置くときにタワーの向き（長辺 = 半径方向）をそろえ、掴むときの向きもそれに合わせて選ぶ
- 目標段数はジェンガのブロックで最大 9〜10 段
- ブロックを 7 個以上使う場合、今のランダム配置（重ならないよう対角線の長さ以上離す）では置ききれない可能性がある。
  配置方法（列に並べる等）を見直す

実装メモ:

5 段以上に向けた課題（Phase 5 または Phase 3 の拡張）:
- 真下向きで届くのは 4 段まで。5 段以上はグリッパを傾けて置く必要がある
- 傾けて置くとブロックも同じだけ傾くので、掴むときも同じ角度で傾けておく必要がある
- 傾けて掴めるのは、ブロックの長辺がロボットから見て半径方向を向いているときだけ。
  ランダムな向きのブロックは、一度真下向きで置き直して向きをそろえ（持ち替え）、傾けて掴み直す

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| Windows 10 + Docker で GPU が認識されない | ドライバ・WSL カーネル更新。最悪 CPU（`MUJOCO_GL=osmesa`）でシミュ・データ収集だけ先に進める |
| GUI が表示できない | 動画出力を基本にし、対話操作は noVNC で行う |
| 5 軸アームのため IK が解けない姿勢がある | 把持姿勢を「真上から」に限定し、ヨー角はブロック向きに合わせて手首回転で調整 |
| 把持が不安定（すべり・貫通） | ブロックサイズ・グリッパ摩擦・ソルバ設定をチューニング。必要ならグリッパに補助的な接触パッドを追加 |
| 高く積むほど到達範囲外になる | アームの到達高さから最大段数を事前に計算し、ブロックサイズを決める |
| 8GB VRAM / 16GB RAM 不足 | 画像解像度を下げる、バッチサイズを下げる、勾配累積を使う |
| LeRobot の API 変更が速い | Dockerfile で lerobot のバージョン（コミット）を固定する |
